01Resolved decisions

These questions were settled before the build. They are load-bearing — changing any of them reopens the design.

Deliverable now Design approved; M1–M8 built and verified end-to-end against MySQL.
Database MySQL 8 (was PostgreSQL in the first draft). Run as the developer's local server, not a container. Prisma provider mysql; long text columns get explicit @db.Text/@db.LongText, and contains filters rely on the utf8mb4_*_ci collation since Prisma's mode: "insensitive" is Postgres-only.
Infrastructure MySQL is the only dependency — no Redis, no Docker. The job queue (originally BullMQ/Redis) is a Job table: workers poll, claim a row with a conditional UPDATE, and process. Rate limiting is a sleep between sends; the daily cap is a COUNT; retries/backoff and the dead-letter state live in columns. Sized for the sandbox volume, not for a high-throughput broker.
Repository New folder email-automation-platform/ under the current directory; fresh git repo.
Tenancy Single organization. No orgId on models. Roles are a flat admin / editor enum on User.
Email provider SES sandbox, low volume. Default runtime provider is a console/mock adapter. The SES adapter is written and tested but disabled by config until the domain is verified and the account leaves sandbox.
SES sandbox constraint

While in sandbox: max 200 recipients / 24 hours, max 1 message/second, and every recipient address must be individually verified. The pipeline enforces all three as hard limits so behaviour does not change shape when the real adapter is switched on — only the numbers move (to config).

02Scope & non-goals

In scope

  • Scheduled campaigns: one-time at a future time, and recurring by cron expression.
  • Event-triggered email via an authenticated webhook (/api/webhooks/trigger/:eventKey).
  • Contacts, lists, list membership; CSV import.
  • Reusable templates with {{variable}} substitution and a preview endpoint.
  • Delivery tracking: sent / delivered / opened / clicked / bounced / complained / failed.
  • Suppression list (unsubscribes + hard bounces + complaints), enforced on every send.
  • Queue with rate limiting, idempotent sends, exponential-backoff retries, dead-letter queue.
  • React dashboard for all of the above, plus a stats view per campaign.

Explicit non-goals (v1)

  • Multi-tenancy / per-customer isolation.
  • Visual drag-and-drop template builder — templates are hand-authored HTML.
  • A/B testing, send-time optimisation, deliverability analytics beyond raw counts.
  • Inbound email / reply parsing.
  • Provider failover at runtime — the interface allows it later; v1 runs one provider.
  • Fine-grained per-resource permissions beyond admin/editor.

03Architecture overview

One Node process type runs the API; a second runs the queue workers and the scheduler. Both share one Prisma client against MySQL, which is the source of truth and the queue.

Processes & deployment units

UnitResponsibilityScale signal
apiREST endpoints, auth, webhook ingestion, enqueues jobsrequest latency
workerConsumes send jobs, renders, checks suppression, calls provider, writes EmailLogqueue depth
schedulerPolls the campaigns table on a 15s tick; enqueues a dispatch job when one is due. Runs inside the worker process; assumes a single instance.n/a (singleton)
mysqlPrimary datastore and the job queue (Job table). Developer's local server, not containerised.connections, disk

Local development

No containers. Install Node and MySQL 8, create the dispatch database, run npm run prisma:deploy then npm run dev (API + worker + web in parallel). A single .env at the repo root is read by every process; .env.example is committed, .env is git-ignored.

04Data model

Prisma schema, trimmed to the single-org shape. No orgId anywhere. Timestamps (createdAt, updatedAt) are on every model but elided below for brevity except where they carry meaning. The outline below is provider-neutral; the committed schema.prisma is MySQL — htmlBody is @db.LongText, textBody/errorMessage/reason are @db.Text, subject is @db.VarChar(300), and the JSON columns carry no default (MySQL forbids it) so every write supplies {}/[] explicitly.

// ---- the ledger ----
model EmailLog {
  id               String      @id @default(cuid())
  campaignId       String?
  triggerId        String?
  contactId        String
  idempotencyKey   String      @unique
  status           EmailStatus @default(QUEUED)
  providerMessageId String?
  errorMessage     String?
  sentAt           DateTime?
  updatedAt        DateTime    @updatedAt
  campaign Campaign? @relation(fields: [campaignId], references: [id])
  trigger  Trigger?  @relation(fields: [triggerId],  references: [id])
  contact  Contact   @relation(fields: [contactId],  references: [id])
  @@index([campaignId, status])
  @@index([contactId])
}
enum EmailStatus { QUEUED SENT DELIVERED OPENED CLICKED BOUNCED COMPLAINED FAILED }

model Unsubscribe {
  id        String   @id @default(cuid())
  contactId String   @unique
  reason    String?
  token     String   @unique          // opaque token in the unsubscribe link
  createdAt DateTime @default(now())
  contact   Contact  @relation(fields: [contactId], references: [id], onDelete: Cascade)
}

// ---- the queue (there is no Redis) ----
model Job {
  id          String    @id @default(cuid())
  queue       String                              // "send-email" | "campaign-dispatch" | "csv-import"
  payload     Json
  status      JobStatus @default(PENDING)         // PENDING ACTIVE COMPLETED FAILED DEAD
  runAt       DateTime  @default(now())           // not eligible until this time (delay + backoff)
  attempts    Int       @default(0)
  maxAttempts Int       @default(1)
  dedupeKey   String?   @unique                   // repeat enqueues collapse to one row
  result      Json?
  lastError   String?   @db.Text
  lockedAt    DateTime?
  lockedBy    String?
  @@index([queue, status, runAt])
}

Notes

  • idempotencyKey is the spine of exactly-once delivery. Format: {campaign|trigger}:{sourceId}:{contactId}:{occurrenceISODate}. For a recurring campaign, occurrenceISODate is the scheduled run's date, so the same contact can receive Monday's and Tuesday's digest but never two of Monday's. (The queue can't store a : in a dedupe key cheaply, so Job.dedupeKey is the same value with : → _.)
  • The Job table is the whole queue. A worker SELECTs due rows for its queue, claims each with UPDATE ... SET status='ACTIVE' WHERE id=? AND status='PENDING' (0 rows → lost the race, skip), processes, then marks COMPLETED / re-schedules with backoff / marks DEAD. A row stuck ACTIVE past 5 min is reclaimed. Safe with N workers; the scheduler still assumes one.
  • Status is a lattice, not a strict line. OPENED implies delivered; a later COMPLAINED can supersede OPENED. The worker only ever advances status; provider webhooks apply terminal states. See fig. 6.2.
  • Suppression is derived, not a table: a contact is suppressed if status != ACTIVE or an Unsubscribe row exists. A single isSuppressed(contactId) helper is the only code path allowed to make that call.
  • HTML is stored raw and sanitised at render time (not on save) so the sanitiser can be upgraded without a data migration.

06Sending pipeline

Two entry points — the scheduler and the trigger webhook — converge on one send-email queue. Every send, regardless of origin, goes through the same worker with the same guarantees.

Queues

All three are Job rows distinguished by the queue column; each has one poller loop. No separate dead-letter queue — a permanently failed row stays as status = DEAD and is surfaced at /api/jobs.

QueueProducerJobPoller settings
campaign-dispatchscheduler tick / send-nowone job per due campaign occurrence; fans out into send-email in batches of 500poll 3s, batch 5, retries 3
send-emailfan-out + trigger webhookone job per (source, contact, occurrence), deduped on the idempotency keypoll 1s, batch 25, minInterval = 1000/SEND_RATE_PER_SEC ms between sends, backoff exponential, attempts 5
csv-import/api/contacts/importparse + upsert contactspoll 2s, batch 1

Guarantees, and how each is met

PropertyMechanism
IdempotencyTwo layers: Job.dedupeKey collapses repeat enqueues to one row, and unique EmailLog.idempotencyKey means the worker's upsert + terminal-status check never sends twice even if a row slips through. Safe under retry and duplicate webhook calls.
Rate limitingThe send poller sleeps 1000 / SEND_RATE_PER_SEC ms after each send (default 1/sec in sandbox). One worker process, so this is the global rate; running two would double it.
Daily capCOUNT(*) FROM EmailLog WHERE sentAt >= todayUTC checked before each send. Over cap → the job is deferred (runAt = next UTC midnight) without consuming a retry.
RetriesUp to SEND_MAX_ATTEMPTS (5); runAt = now + SEND_BACKOFF_MS · 2^(attempt-1). Provider errors are classified: transient (throttling, 5xx) retry; permanent (invalid address, sandbox-unverified, render error) go straight to DEAD.
SuppressionisSuppressed() called inside the worker immediately before render. Never trust the enqueue-time check — a contact can unsubscribe while the job sits in the queue.
Partial retryFan-out is per-contact jobs, so one bad address never blocks the campaign; only that job retries or goes DEAD.
Poison-message safetyRender errors (bad template syntax, missing declared var) are permanent → DEAD with the offending variable named in lastError.
Crash recoveryattempts is incremented at claim time, so a worker that dies mid-send still burns an attempt — no infinite poison loop. A row left ACTIVE > 5 min is reset to PENDING.

Scheduler detail

No repeatable-job machinery — a 15 s tick reads every SCHEDULED campaign straight from MySQL. A ONCE campaign is due once sendAt has passed and lastRunAt is null. A RECURRING one walks cron-parser occurrences after lastRunAt (in SCHEDULER_TIMEZONE) up to now, enqueuing a campaign-dispatch job per missed occurrence, then advances lastRunAt. Each dispatch job carries a dedupe key (disp:{id}:{occurrenceISO}) so a double tick is a no-op, and fanOutCampaign re-checks status, so pause/resume is a pure DB write.

07Provider abstraction

The worker depends only on this interface. The concrete adapter is chosen at boot from EMAIL_PROVIDER (mock | smtp | ses). The smtp adapter (nodemailer) reads SMTP_HOST/PORT/SECURE/USER/PASS and classifies 5xx / EAUTH / EENVELOPE as permanent, 4xx and connection errors as transient; like mock it has no delivery callback.

interface EmailProvider {
  readonly name: string;

  send(msg: OutboundMessage): Promise<SendResult>;

  // Parse a provider callback (SNS body) into normalised events.
  parseWebhook(req: RawRequest): DeliveryEvent[];
}

interface OutboundMessage {
  to: string;
  from: string;              // configured verified sender
  subject: string;
  html: string;
  text: string;
  headers: Record<string, string>;   // List-Unsubscribe, etc.
  tags: { emailLogId: string };       // round-tripped via provider metadata
}

interface SendResult { providerMessageId: string; }

type DeliveryEvent =
  | { type: 'delivered';  providerMessageId: string }
  | { type: 'bounced';    providerMessageId: string; hard: boolean }
  | { type: 'complained'; providerMessageId: string };

class PermanentSendError extends Error {}   // -> DLQ, no retry
class TransientSendError extends Error {}   // -> retry with backoff

MockProvider (default)

  • Writes the rendered message to disk under ./.mail-outbox/ and logs a one-line summary.
  • Returns a synthetic providerMessageId (mock-{uuid}).
  • Optional MOCK_FAIL_RATE to exercise retry/DLQ paths in dev.
  • No webhook; a dev-only endpoint can simulate delivery events.

SesProvider (built, disabled)

  • @aws-sdk/client-sesv2, SendEmailCommand with configuration set for event publishing.
  • parseWebhook verifies the SNS signature, handles subscription confirmation, maps SES notification types.
  • Classifies Throttling / ServiceUnavailable as transient; MessageRejected for unverified recipients as permanent (expected in sandbox).

08Tracking & compliance

Rendering & link rewriting

  • Template rendered with a logic-less engine (Handlebars-style {{var}} only — no partials, no helpers that can execute). Missing declared variables raise a permanent render error.
  • Output HTML sanitised with a strict allowlist (no <script>, no event handler attributes, no javascript: URLs).
  • Every <a href> is rewritten to /api/track/click/:logId?u=<signed>. The original URL is HMAC-signed so the redirect cannot be turned into an open redirect.
  • A tracking pixel <img src="/api/track/open/:logId.png"> is appended before </body>.
  • Both the link rewriting and the pixel are gated on EMAIL_TRACKING (default on). Set it to false to send clean, untracked mail for better primary-inbox placement, trading away all open/click stats.
  • Every message gets a List-Unsubscribe header and a visible unsubscribe link (/api/unsubscribe/:token) — template validation rejects a template that omits the {{unsubscribe_url}} variable.
Compliance baseline

CAN-SPAM / GDPR: physical sender address in the footer, functioning unsubscribe honoured within the send pipeline immediately (suppression is derived, not batch-processed), hard bounces and complaints auto-suppress on webhook receipt. Open/click tracking is on by default — see Still open for the consent question.

Webhook ingestion

/api/webhooks/ses verifies the SNS signature, looks up the EmailLog by providerMessageId, advances status, and on bounced(hard) / complained sets Contact.status and the send pipeline stops targeting that address on the next evaluation. Events are processed idempotently (a delivery event arriving twice is a no-op).

10Observability & ops

  • Logging — pino, JSON, one logger per process. Every HTTP request and every job carries a requestId / jobId; the send path logs emailLogId so a single email is greppable end to end.
  • Error tracking — Sentry in api and worker; a job going DEAD logs at error and raises a Sentry event.
  • Queue visibility — GET /api/jobs (JWT admin) returns per-queue/status counts and the most recent rows; the dashboard's Settings page renders it with a one-click retry. No external dashboard to run.
  • Metrics — counters for sent / failed / suppressed / dead-lettered and a gauge for daily-cap usage, exposed at /metrics (Prometheus text format).
  • Secrets — all via environment; .env git-ignored; production secrets from the host's secret manager, never baked into images.
  • Migrations — Prisma Migrate; migrate deploy runs as a pre-start step. Backwards-compatible migrations only, so a rolling deploy never runs old code against a new schema it can't read.

13Still open

None of these block M1–M4. They need an answer before the milestone in brackets.

Needs a decision
  • Sender identity — which domain sends, and who owns the DNS to add SPF/DKIM/DMARC records? [before M9]

  • Production host — where do the two Node processes and the managed MySQL run? Affects the deploy notes. [before M9]
